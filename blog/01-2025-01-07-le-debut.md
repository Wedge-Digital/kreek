## C'est quoi kreek ?

Une plateforme de gestion de compétitions sportives amateurs. L'idée vient d'un constat simple : organiser une ligue ou un tournoi entre amis ou dans un club, c'est souvent un bricolage de feuilles Excel, de groupes WhatsApp et d'outils génériques mal adaptés. Kreek, c'est une application web pour gérer ça proprement — créer des compétitions, former des équipes, suivre les classements.

## Pourquoi Rust ?

J'aurais pu partir sur ce que je connais déjà. Mais l'un des objectifs de ce projet est d'apprendre Rust sérieusement, pas à travers des exercices artificiels mais en construisant quelque chose de réel.

Rust a la réputation d'être difficile au démarrage. Le borrow checker, la gestion manuelle de la durée de vie des références, l'absence de garbage collector — c'est déroutant quand on vient d'autres langages. Mais c'est précisément ce qui rend l'apprentissage utile : les erreurs que Rust refuse de compiler sont souvent des bugs silencieux dans d'autres langages.

Premier dépendance ajoutée au `Cargo.toml` : `ulid`. Une seule ligne.

```toml
[dependencies]
ulid = "1.1.3"
```

## La première entité : Team

Avant même de penser à la base de données ou au serveur HTTP, j'ai commencé par modéliser le domaine. La première entité qui existe, c'est `Team` :

```rust
pub struct Team {
    pub entity_id: Ulid,
    pub coach_id: Ulid,
    pub nom: String,
}
```

Trois champs. Un identifiant unique pour l'équipe, un identifiant pour le coach, un nom. Simple.

J'utilise `Ulid` plutôt que `Uuid`. Un ULID est triable chronologiquement — les identifiants générés plus tard sont lexicographiquement plus grands. C'est pratique pour les requêtes de pagination et pour déboguer : on voit immédiatement l'ordre de création sans regarder un timestamp séparé.

## Le bus de commandes

Ce qui est moins habituel pour un "premier commit", c'est la structure `framework/bus/` que j'ai posée en même temps.

L'idée : plutôt que des appels directs entre composants, les actions de l'application transitent par un dispatcher. Un handler s'enregistre pour un type de commande, et le dispatcher l'appelle au bon moment.

```rust
pub struct CommandDispatcher {
    executors: HashMap<TypeId, fn(&Command)>
}

impl CommandDispatcher {
    pub fn register(&mut self, t_id: TypeId, executor: fn(&Command)) {
        self.executors.insert(t_id, executor);
    }

    pub fn dispatch(&self, cmd: &Command) {
        let t_id = cmd.type_id();
        match self.executors.get(&t_id) {
            None => {}
            Some(executor_candidate) => { executor_candidate(cmd) }
        }
    }
}
```

Le mécanisme repose sur `TypeId` de la bibliothèque standard — chaque type Rust a un identifiant unique à l'exécution. Le dispatcher fait correspondre le type de la commande reçue avec le handler enregistré pour ce type.

J'ai aussi posé un trait `Middleware` avec chaîne de responsabilité :

```rust
pub trait Middleware {
    type MiddlewareType;
    fn handle(&mut self, message: BaseMessage) -> BaseMessage;
    fn set_next(&mut self, next: Self::MiddlewareType);
    fn get_next(&self) -> Option<&Self::MiddlewareType>;
}
```

L'intention était de pouvoir composer des transformations sur les messages avant qu'ils n'atteignent leur destination — logging, validation, enrichissement.

## Ce que j'aurais fait différemment

En relisant ce commit aujourd'hui, quelques choses me font sourire.

D'abord, `Command::new()` qui s'appelle elle-même récursivement — une stack overflow garantie si on avait tenté de l'instancier. Rust compile quand même : une récursion infinie n'est pas une erreur de compilation, c'est une erreur d'exécution.

```rust
impl Command {
    pub fn new() -> Command {
        return Command::new(); // ← boucle infinie
    }
}
```

Ensuite, le `main.rs` de l'époque :

```rust
fn main() {
    println!("Hello, world!");
    let team = team_creation::create_team::Team::nouvelle_team(
        "Les Bleus".to_string(),
        ulid::Ulid::new()
    );
    team.afficher();
}
```

Un `println!` "Hello world" et une équipe qui s'affiche dans le terminal. Pas de serveur, pas de base de données, pas d'API. C'est le point zéro.

## La structure de fichiers

```
src/
├── main.rs
├── framework/
│   └── bus/
│       ├── bus.rs              # trait Bus (vide)
│       ├── message.rs          # trait Message + BaseMessage
│       ├── dispatcher.rs
│       ├── executor.rs
│       ├── command/
│       │   ├── command_dispatcher.rs
│       │   └── command_type.rs
│       ├── middleware/
│       │   └── middleware.rs
│       └── tests/
└── app/
    ├── team_creation/
    │   ├── create_team.rs      # struct Team
    │   └── tests/
    └── infra/
```

La séparation `framework/` (infrastructure technique générique) vs `app/` (domaine métier) est là dès le début. C'est une intention : garder le domaine pur, indépendant du framework.

## Ce que ce commit établit

Pas grand chose qui tourne. Mais les intentions sont là :
- ULID pour les identifiants
- Domaine isolé du framework
- Un bus de commandes comme colonne vertébrale de la communication entre composants

Le prochain commit va repartir sur des bases plus solides : l'event sourcing entre en jeu.
